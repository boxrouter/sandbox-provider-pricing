# Beam metadata probe report

**Status: findings complete; cleanup is stuck on one sandbox.** Probes ran 2026-11-23 from the devbox, with provider-slot run beam; all app REST calls were GET-only. No Beam token was transferred. All evidence traces are redacted.

## 2. Stub identity, input limits, and latency

- The SDK Sandbox name argument set to probe-<RUN> sends app_name="probe-<RUN>"; its protobuf stub name is "sandbox". Sandbox.create() sends force_create=True. Two creates with identical visible configuration therefore produced different stub_id values. Changing app_name also changed app_id when the app name was unique.
- Replaying the identical GetOrCreateStubRequest with force_create=False twice returned the same stub_id both times. With force_create=True, repeated identical requests returned new IDs. With force_create=False, changing protobuf name, app_name, env, or extra individually returned a different stub ID for each tested variant.
- Character samples containing /, !#$%^&*(), café, and 雪 were accepted in name, app_name, env text, and JSON extra. This proves only those sample characters, not the full allowed charset.
- Length tests: name at 8,209 characters returned ok=False, err_msg="Failed to get or create stub"; app_name at 8,207 returned ok=False, err_msg="Failed to get or create app". An env value of 8,192 characters and an extra JSON string of 8,206 characters were accepted. **Maximum lengths are not determined**; the exact upper boundary was not searched. The workspace limits response included max_replicas=100, which is not a distinct-stub quota. A maximum number of distinct stubs per workspace is **not determined**; no such quota was established by the docs or these probes.
- 32 pairs round-tripped in extra through the app config, and in env through /proc/1/environ. A 448-byte metadata file also round-tripped exactly inside the sandbox; neither in-container option supplies a workspace-wide metadata read.

Create latency was measured as the sequential GetOrCreateStub + CreatePod RPC wall time, with image build and file sync excluded. Five unique-config and five shared-config creates were interleaved on the same devbox. Median unique: **70.751 ms**; median shared: **70.408 ms** (unique +0.343 ms). Every measured call logged its exact two-RPC list in traces/meta_latency-9bd8f929.jsonl. Label these numbers **“devbox, relative only, not certified, not for publication.”** This small difference is not a general latency claim.

## 3. Replay and CreatePod idempotency

Installed CreatePodRequest fields are exactly stub_id, optional image_id, optional checkpoint_id, and optional machine_id; there is no native idempotency-key field. I sent two CreatePodRequest(stub_id=<same>) calls with the same x-beta9-request-id via beta9.channel.request_metadata. Both returned ok=True and different container IDs; the subsequent list contained both. The gateway did not deduplicate that request id. CreatePodResponse fields are ok, container_id, error_msg, stub_id, task_id, and app_id; observed sandbox task_id was empty. Evidence: traces/meta_live-f57012de.jsonl; request fields are in beta9/clients/pod/__init__.py.

## 4. Container listing and lifecycle timing

ListContainersRequest() has no filter or pagination fields in the pinned SDK. The response contains workspace-wide rows; observed own IDs all had the sandbox- prefix and empty deployment_id. ListContainers does not return stub_type; the app REST representation does. No deployment/function container was present as a comparison sample, so whether the gateway list includes non-sandbox containers, and a complete discriminator for them, are **not determined**. Observed statuses were PENDING, RUNNING, and STOPPING; SCHEDULING was not observed. Pending and stopping rows were present in the list. After stop, the row disappeared in about 0.54–0.58 seconds in ordinary probes, while SandboxStatus advanced from stopping to exited. A sandbox reached RUNNING 0.552 seconds after the CreatePod response in the lifecycle trace. These are observations, not fixed-wait recommendations. Evidence: traces/meta_live-f57012de.jsonl and traces/meta_followup-200f5d16.jsonl.

## 5. Timestamps and app id

CreatePodResponse returned app_id but had empty task_id; it has no scheduled_at or started_at fields. ListContainers (and GET /container/{ws}) returned scheduled_at and started_at. In one pending row started_at was the Unix epoch sentinel; once running it had a current timestamp. The field names indicate schedule/start times, but the probe did not establish a stronger semantic guarantee. The adapter can read those times later while the container remains listed. After disappearance, no container row remains to retrieve its creation time; app created_at is the app record’s time, not a demonstrated per-container creation time.

## 6. Recommendation

For Beam-backed metadata, put the label map in extra and assign a **unique app_name per sandbox**. Save the app_id associated with the sandbox when creating it. Then one GET /app/{ws}/{appId} returns stub.config.extra for a single lookup. For a list, GET /container/{ws} once and GET /app/{ws}/latest?limit=100 once, join container app_id to app id, and filter by status and labels. The live test verified this join for two running sandboxes and one app-list response containing 43 apps with no next page. A strict 100-entry pagination ceiling was not exercised, so the at-most-two-call guarantee at exactly 100 remains conditional on Beam returning those rows in one limit=100 page. If the adapter uses only the high-level SDK result and does not retain app_id, a single-container lookup by container id requires a second GET to resolve it. Reusing one app_name for several differing stubs can replace the app’s current config, so use unique app names when labels must remain per-sandbox. Using env or a file instead requires reading inside each sandbox and does not provide an efficient workspace list.

## 7. Cleanup proof

All created sandboxes received StopContainer in their finally cleanup. The final read-only check in traces/meta_final_cleanup-7d8e8660.jsonl found one owned container, sandbox-cbc3357f-9020-4eba-b5a6-0ba3b2d27ea3-bee026c6, still in STOPPING; SandboxStatus also returned status='stopping', exit_code=-1. StopContainer had returned ok=True; a second stop request and 60 seconds of half-second polling did not clear it (traces/meta_cleanup-ac80c60f.jsonl). No owned container was RUNNING, but termination is not confirmed. This is reported stuck to the lead; no other lane’s container was stopped.
