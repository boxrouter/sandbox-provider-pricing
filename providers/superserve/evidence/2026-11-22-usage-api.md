# Superserve's per-sandbox usage API

**Date:** 2026-11-22. **Provider:** Superserve (one BoxRouter team, legacy pay-as-you-go
catalog). **Result:** `GET /billing/usage/summary` and `GET /billing/usage/details` report one
sandbox's compute usage and its gross compute cost in Superserve's own figure. A pause/resume
sandbox bills as two closed intervals; a running sandbox has one open interval whose amount
grows to the read's cutoff. The figure settled at the delete itself: the first read 1.8 s after
it, and eleven reads over the next five minutes, all returned the same total. Shared storage is
not allocated to a sandbox (`storage_cost_attribution: "unavailable_shared"` — measured on the
run below: it stays unbilled). Corrections stay at team level (`team_has_corrections`), none of
their amount reaches a sandbox.

## Question

Does Superserve report an exact per-sandbox cost — the provider's own figure — that Cloud can
carry instead of pricing audit-log rows at list rates?

## Method

Four sandboxes were created through the REST API on `use` (the `superserve/base` template, 2
vCPU / 4096 MiB), each deleted by the script that created it. The usage endpoints were read
throughout: `GET /billing/usage/summary?sandbox_id=<id>` every ~15 s while each ran and for
5 min after delete, `GET /billing/usage/details?sandbox_id=<id>` for the interval records. Raw
answers: `raw/2026-11-22-usage-api/` (sandbox ids are not sensitive; `access_token`,
`routing_hint` and the key are absent from every file).

- **A — short run, deleted.** `b7e37b87-a1f3-47cc-9708-293b7a86f3cd`, ran 153 s.
- **B2 — pause, resume, deleted.** `ce43ffbc-710d-4721-bab3-0777ecc1e73c`, created with a
  nonzero `auto_delete_seconds` (0 deletes at the first pause instead).
- **S — running across polls.** `13650c8b-cfd2-4d94-b25a-a1e4b8e23411`, read six times while
  running, then deleted and read again.
- **D — created from a snapshot** of S (`6b41f7ca-a4c8-4145-b66d-b8c57f351949`),
  `b00bafae-5ce5-4a68-8883-6068ac6dd2f2`, then deleted. Its own compute was its own record;
  `GET /billing/usage/storage-references` answered empty references with
  `cost_attribution: "unavailable_shared"` for the sandbox and the snapshot.

## Results

```json
  "period_status": "open",
  "as_of": "2026-11-22T22:44:19.449672Z", "read_at": "2026-11-22T22:44:19.449672Z",

  "cost_basis": "provisional_current_catalog",
  "price": {"vcpu_usd": "0.000014000000", "memory_usd": "0.000004500000",
            "unit": "second", "currency": "USD", "plan_key": "payg",

  "team_has_corrections": false,

```

`details` returns `intervals` (with `id`, `started_at`/`ended_at`, `effective_start`/
`effective_end`, `end_reason`, `vcpu_count`, `vcpu_milli`, `memory_mib`, `vcpu_seconds`,
`memory_gib_seconds`, `gross_compute_cost_usd`) plus `next_cursor` and the same period
metadata. A sandbox with no record answers `404 {"error":{"code":"not_found","message":
"Usage not found"}}`; a malformed id answers `400 bad_request`. `period_start`/`period_end`
and `through` query parameters work (an explicit `through` returned a lower provisional total
with `usage_through` at the cutoff).

### Per scenario

- **A:** one interval, `started_at` 22:38:55.378 → `ended_at` 22:41:28.524,
  `end_reason: "deleted"`, cost 0.007044724740 = the summary's total to the last digit. The
  first post-delete summary at 22:41:30.33 (1.8 s after the delete returned) already held it;
  all twelve reads to 22:44:19 were identical. **Settled in under 2 s.**
- **B2:** two intervals — 22:40:29.3→22:41:16.0 `paused` (0.002146203462) and
  22:41:21.9→22:45:16.6 `paused` (0.010797878540); the delete while paused added no row and the
  last interval keeps `end_reason: "paused"`. Summary total 0.012944082002 = the exact sum.
- **S:** one open interval (`ended_at: null`, `end_reason: null`) whose `effective_end` is the
  read's own cutoff; the total grew each poll: 0.0041636 → 0.0076923 over 77 s. After delete the
  interval closed `end_reason: "deleted"` and the total froze at 0.018513929074.
- **D:** a sandbox made from a snapshot has its own new usage record — 0.010687403054 for its
  own run, `end_reason: "deleted"`. The snapshot's identity appears nowhere in it.
- **Cleanup:** `GET /sandboxes` after the run: `[]`. Nothing remained.

### Semantics stated by the shipped OpenAPI

- `gross_compute_cost_usd` is the sandbox's compute usage priced at the catalog in effect; open
  periods are provisional (`cost_basis: "provisional_current_catalog"`), finalized periods use
  retained invoice unit prices.
- `storage_cost_attribution` has one enum value, `unavailable_shared`: shared storage is a
  team-level charge and is never allocated to a sandbox. Storage is not billed today
  (`billable: false` in the public pricing data and in every series bucket measured).
- `team_has_corrections` flags team-level retroactive corrections; the correction amounts stay
  at team level and are not allocated to a sandbox.
- Detail pages can change after corrections, and cursors can be invalidated by pricing or
  period-status changes.
- Usage before the API's own launch cutoff (`usage_from`, 2026-11-19T22:00:00Z on this team) is
  excluded; a sandbox that ended before it has no record and answers `Usage not found`.

## Verdict

Superserve reports the per-sandbox cost it owns: one figure (`gross_compute_cost_usd`, compute
only — shared storage has no per-sandbox amount) that is exact against its own interval records
and settles at the delete, not later. It is the reported cost for Cloud. Where Superserve has no
record — an unmetered sandbox, one that ended before the usage API's cutoff — the cost is
unknown; nothing else (audit rows, list rates) should substitute for it.

The figure matched list rates on this team (`price.vcpu_usd` 0.000014, `price.memory_usd`
0.0000045 per second — the published payg rates), measured on a list-rate plan; whether a
negotiated-rate team's figure differs is unmeasured.
